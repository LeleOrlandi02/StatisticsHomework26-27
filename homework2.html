1 BIP-39: Mnemonic Sentence & 512-bit Seed Generation
Key Stretching (PBKDF2-HMAC-SHA512)

Entropy ($128$ or $256$ bits) is combined with a short SHA-256 checksum ($4$ or $8$ bits) and grouped into 11-bit chunks, each indexing a word in the $2048$-word dictionary. The mnemonic is transformed into a cryptographically secure 512-bit (64-byte) binary seed via PBKDF2-HMAC-SHA512 with 2048 iterations and salt "mnemonic" + passphrase.

2 BIP-32 & BIP-44: Hierarchical Deterministic Key Derivation
Key Derivation Function (CKDpriv)

BIP-32 derives a tree of keys from the master seed using HMAC-SHA512. The standard Ethereum derivation path defined in BIP-44 is m / 44' / 60' / 0' / 0 / i, where 44' is the BIP-44 purpose, 60' is Ethereum's coin type, 0' is the account, 0 is external chain, and i is the address index. Hardened indices ($i \ge 2^{31}$) prevent compromised child keys from leaking parent private keys.

3 secp256k1: Elliptic-Curve Public-Key Cryptography
Asymmetric Cryptography (ECDLP)

The public key is computed as a scalar multiplication on the elliptic curve y² ≡ x³ + 7 (mod p): Q = k × G. Point addition and doubling are computed over the finite field $\mathbb{F}_p$. Ethereum uses the 65-byte uncompressed public key (0x04 || x || y), where the 0x04 prefix identifies uncompressed representation.

5 EIP-55: Mixed-Case Checksum Encoding
Error-Detecting Checksum Code

To prevent catastrophic typo mistakes during copy-pasting, EIP-55 introduces mixed-case capitalization. The lowercase address string (without 0x) is hashed with Keccak-256. For each character $i$: if it is a letter (a-f) and the $i$-th nibble of the hash is $\ge 8$, it is converted to uppercase; otherwise it remains lowercase.

2. Conceptual Taxonomy: Clarifying the 5 Core Primitives

A rigorous distinction between key generation, key derivation, asymmetric public-key cryptography, hashing, checksums, and encoding.

🔑

Key Generation vs. Derivation

Entropy Creation vs. Deterministic Expansion

Key Generation creates brand-new unpredictability using a Cryptographically Secure Pseudo-Random Number Generator (CSPRNG). In Ethereum, 128 or 256 bits of true physical/OS entropy are generated once.

Key Derivation is a deterministic algorithm (KDF/PRF like PBKDF2 or HMAC-SHA512) that takes an existing secret and deterministically computes one or infinite child keys. Given the exact same mnemonic and derivation path, the same keys are always reproduced.

  • Reversible? No (One-way)
  • Deterministic? Generation: No • Derivation: Yes
  • Ethereum Primitive: CSPRNG → BIP-39 → BIP-32
🔒

Public-Key Cryptography

Asymmetric Trapdoor Functions & Signatures

Asymmetric cryptography relies on mathematical hard problems. On secp256k1, multiplying a private scalar $k$ by generator point $G$ gives public key $Q = kG$. While computing $Q$ takes fractions of a millisecond, recovering $k$ from $Q$ requires solving the Elliptic Curve Discrete Logarithm Problem (ECDLP), which is computationally infeasible ($O(2^{128})$ operations with Pollard's rho).

This allows transaction signing via ECDSA: proving ownership without ever revealing the private key.

  • Trapdoor Inverse? Yes (With private key)
  • Mathematical Basis: ECDLP on secp256k1
  • Ethereum Primitive: ECDSA & secp256k1
⚡

Cryptographic Hashing

Irreversible Fixed-Length Compression

A cryptographic hash function takes an arbitrary-length byte stream and produces a fixed-size digest (e.g. 256 bits). Crucial security properties:
1. Pre-image resistance: impossible to find $m$ given $h = H(m)$.
2. Second pre-image resistance: impossible to find $m_2 \ne m_1$ such that $H(m_1) = H(m_2)$.
3. Collision resistance: impossible to find any pair $(m_1, m_2)$ with $H(m_1) = H(m_2)$.

  • Invertible? Strictly Impossible
  • Output Size: Fixed 256 bits (32 bytes)
  • Ethereum Primitive: Keccak-256
🛡️

Checksums

Redundancy for Human Error Detection

Checksums are error-detecting codes. Unlike cryptographic hashes which protect against malicious adversaries altering data, checksums are engineered to detect accidental human typos, letter transpositions, and cut-and-paste omissions.

EIP-55 encodes error detection directly into the capitalization of the hex characters, ensuring 100% detection of single-character errors without requiring extra characters or breaking legacy hexadecimal formats.

  • Primary Goal: Detect transcription typos
  • Length Overhead: 0 extra characters (in-band)
  • Ethereum Primitive: EIP-55 mixed-case
🔤

Encoding

Bijective, Reversible Data Formatting

Encoding is a completely reversible, 1-to-1 bijection between raw binary data and a character representation suitable for display or transmission.

Examples include Hexadecimal (base-16), Base58Check (Bitcoin), and Bech32. Encoding requires no secret key and provides zero confidentiality; its purpose is purely syntactic compatibility.

  • Reversible? Yes, 100% reversible
  • Requires Secret? No
  • Ethereum Primitive: Hexadecimal (0x...)

3. Empirical Statistical Laboratory

Testing the Strict Avalanche Criterion (SAC), address space size, and collision probabilities under the Birthday Paradox.

A Strict Avalanche Criterion (SAC) & Hamming Distance
Statistical Diffusion

A fundamental requirement for any cryptographic hash or derivation function is the Strict Avalanche Criterion (SAC): flipping a single bit in the input must cause each output bit to flip independently with probability $p = 0.5$. The number of flipped bits is the Hamming Distance $d_H(H_1, H_2) = \text{wt}(H_1 \oplus H_2)$, which follows a Binomial distribution $B(256, 0.5)$ with expected mean $\mu = 128$ and variance $\sigma^2 = 64$.

Combinatorial Probability

An Ethereum address is 20 bytes (160 bits). The total address space contains $N = 2^{160} \approx 1.4615 \times 10^{48}$ possible addresses. By the Birthday Paradox, the probability of finding at least one collision among $n$ randomly generated addresses is approximated by:
P(collision) ≈ 1 − exp(− n² / (2 × 2¹&sup6;&sup0;)) A 50% chance of a collision requires $n \approx \sqrt{2 \ln(2)} \cdot 2^{80} \approx 1.177 \times 2^{80} \approx 1.42 \times 10^{24}$ addresses.

4. Temporal & Historical Context

Placing public-key cryptography, hash standards, and hierarchical deterministic wallet technologies in chronological context.

1977

RSA (Rivest, Shamir, Adleman)

First practical public-key cryptosystem based on the hardness of factoring large composite integers. Marked the dawn of modern asymmetric cryptography.

2001

SHA-2 / SHA-512 (NIST FIPS 180-2)

Standardized by NIST based on the Merkle-Damgård construction. While robust, Merkle-Damgård hashes are inherently susceptible to length-extension attacks without HMAC wrappers.

2012

BIP-32: Hierarchical Deterministic Wallets

Introduced by Pieter Wuille for Bitcoin. Allowed an entire tree of keypairs to be derived from a single master seed without needing continuous new backups.

2013

BIP-39: Mnemonic Words for Deterministic Wallets

Created by Marek Palatinus (Slush), Pavol Rusnak, and the Trezor team. Replaced raw hexadecimal seeds with human-friendly 12- or 24-word phrases and PBKDF2 key stretching.

2014

BIP-44: Multi-Account Hierarchy for HD Wallets

Standardized structured derivation paths (m / purpose' / coin_type' / account' / change / index) enabling a single seed to organize multiple currencies and accounts cleanly.

August 2015

NIST Standardizes SHA-3 (FIPS 202)

Following a multi-year competition won by the Keccak algorithm (designed by Bertoni, Daemen, Peeters, and Van Assche). Utilizes the revolutionary Sponge Construction.

2016

EIP-55: Mixed-Case Checksum Addresses

Proposed by Vitalik Buterin. Implemented backward-compatible error detection directly into Ethereum addresses by capitalizing hex characters based on their Keccak-256 hash.

The Crucial Difference: Keccak-256 vs. NIST SHA3-256

When Ethereum was developed in 2014, the team chose the winning Keccak algorithm. However, NIST later finalized FIPS 202 in August 2015 and added domain separation padding:
• Ethereum Keccak-256 uses the original submission padding suffix 0x01 (0b01).
• NIST SHA3-256 uses the standardized padding suffix 0x06 (0b0110).
Because of this single padding difference, Keccak-256(m) ≠ SHA3-256(m) for any input!

5. Architectural Rationale: Why Not A Single Algorithm?

Why Ethereum wallets combine multiple specialized cryptographic primitives rather than forcing one algorithm to do everything.

BIP-39 / BIP-32 / BIP-44

Key Management & Derivation

Role: Human usability and infinite deterministic tree expansion.

Raw 256-bit keys cannot be written down safely by users. BIP-39 converts entropy to memorable words with checksum protection. BIP-32 and BIP-44 allow a single root seed to derive millions of independent accounts and addresses. Without BIP-32, every new transaction or account would require generating and backing up a new private key.

secp256k1 (ECDSA)

Asymmetric Relationship & Signatures

Role: Identity, authorization, and non-repudiation.

A hash function cannot sign a transaction. Public-key cryptography requires a mathematical trapdoor (the discrete log problem) where $Q = kG$ can be computed by anyone, but $k$ cannot be deduced. Transactions are signed using $k$, producing $(r, s, v)$ which anyone can verify using $Q$.

Keccak-256

One-Way Compression & Privacy

Role: State compression and pre-image obfuscation.

An uncompressed public key is 65 bytes ($520$ bits). Storing 65 bytes for every account in Ethereum's world state Patricia Trie would bloat database storage prohibitively. Keccak compresses it to 20 bytes ($160$ bits), reducing storage costs while providing pre-image resistance.

EIP-55

Error-Detecting Checksum

Role: Human-factor typo protection without breaking APIs.

Bitcoin uses Base58Check which appends 4 bytes of hash checksum. However, Ethereum already had thousands of smart contracts and dApps accepting 40-character hex strings (0x...). Vitalik Buterin designed EIP-55 so that hex parsers (which ignore case) still parse the address identically, while wallet UIs reject typos.

6. Software Wallets in Practice: MetaMask, Rabby, Exodus & Rainbow

How modern Web3 wallet clients manage keys, storage encryption, derivation paths, and transaction signing.

MetaMask & Rabby (Browser Extensions)

MetaMask and Rabby store the BIP-39 mnemonic in the browser's encrypted storage (Vault) using AES-256-GCM, encrypted by a user password stretched with PBKDF2 (10,000 iterations).

When users click "Add Account", MetaMask simply increments the address index $i$ in m/44'/60'/0'/0/i. The master seed never leaves local storage.

Rainbow & Exodus (Mobile & Multi-Chain)

Rainbow and Exodus leverage native hardware security: Apple Secure Enclave on iOS and Android Keystore backed by biometric authentication (FaceID / Fingerprint).

Multi-currency wallets like Exodus change the BIP-44 coin type: m/44'/60'/... for Ethereum, m/44'/0'/... for Bitcoin, and m/44'/501'/... for Solana, all derived from a single backup phrase!

Hardware Wallets (Ledger & Trezor)

Hardware wallets isolate the seed inside a certified Secure Element (Common Criteria EAL6+).

When interacting with dApps, the transaction payload is sent via USB/Bluetooth to the device, which displays the recipient and value on an isolated screen, signs the Keccak-256 hash using the internal private key, and returns only the $(r, s, v)$ signature.
